## What shipped 2026-07-29/30: founder-outreach feature (14/14 tasks)

Full feature, plan-doc-driven (`docs/superpowers/plans/2026-07-29-founder-outreach.md`, all 14 tasks marked done with result notes inline), two PRs (#3 tasks 1-5, #4 tasks 6-14), both merged and deployed/verified live on EC2:

- **Pipeline:** sector classification (crypto/web3/defi/fintech/ai) piggybacked on the existing `llm_judge` verdict call → Apollo.io company lookup (employee count) → LLM-drafted personalized email → Gmail API draft creation (raw REST, stdlib `email.mime`, OAuth2 refresh-token flow) → Telegram notification. Wired into `process_job` as a fire-and-forget step (never breaks the existing tailoring contract) plus a dedicated `--outreach --job-id N [--founder-email EMAIL]` CLI path.
- **Triggers:** automatic (on every newly-tailored job, gated on sector+size+founder-email), Telegram reply (`outreach` / `outreach: email@x.com`), dashboard button (`POST /api/jobs/{id}/outreach`, with an override-email input).
- **Apollo free tier cannot return founder_name/founder_email at all** — every person-search endpoint (`/mixed_people/search`, `/people/search`, `/people/match`, `/mixed_companies/search`) 403s with `API_INACCESSIBLE`, confirmed by probing all four directly. Only `employee_count` (org search) works. The `founder_email_override` mechanism (dashboard input / Telegram `outreach: email` reply) is the only way outreach actually produces a draft right now — this is why item 1 above matters.
- **Real bug found and fixed via live testing, not just unit tests:** `draft_outreach_email`'s hardcoded 20s LLM-call timeout was too tight for real JD+resume-sized prompts (measured ~35s actual completion against a real job). `llm_judge` sends similarly-sized prompts at the same 20s default but gets away with it because it has a rule-based fallback on timeout; `draft_outreach_email` has none by design (a non-personalized "draft" isn't worth creating), so it needed real headroom — bumped to 45s.
- **Gmail OAuth gotcha:** the Google Cloud Console OAuth client was created as **"Web application" type, not "Desktop app"** despite the app being named "jobwatch" — Web app clients require every redirect URI explicitly whitelisted (`http://localhost:8765` had to be added under "Authorized redirect URIs"); Desktop app clients auto-accept any localhost port with zero registration. Worth checking client type first if this ever needs re-auth.
- **Verified against the real system, not just tests:** ran `--outreach --job-id` against real production job #9684 (Weave), confirmed a real Gmail draft via a direct Gmail API call (correct recipient, personalized subject, resume PDF attached via `multipart/mixed`), then cleaned up (deleted the test draft, reset the job's outreach fields) so it doesn't pollute real data.
- Credentials (`APOLLO_API_KEY`, `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`) added to both the laptop's and EC2's `.env` — confirmed loading correctly server-side via a live import check.
- **Not yet confirmed:** a live human reply of "outreach" to a real Telegram notification (needs a real device, Claude can't do this) — the Go-side argv-passing is unit-tested and the Python side it calls is live-verified, so this is a device-confirmation step, not a functional gap.

**Also clarified for Mayur mid-session:** the ~4500 `status='ignored'` jobs he saw in the DB are not missed notifications — `poller.go` inserts *every* fetched job unconditionally, tagging it `new` or `ignored` at insert time based on the title/location filter; only `new` jobs ever reach Telegram/tailoring. The DB keeps the full fetch history for dedup/audit, not just what passed. This is expected behavior, not a bug, and explains why adding 20 companies produced thousands of ignored rows (big companies post across every department/country, most of which correctly fail the include/location filter).

## Process note for next session

All five tasks above went through the full `brainstorming → writing-plans → executing-plans` cycle, each in a **fresh git branch off current `master`** (not reusing this session's starting worktree branch, which turned out to already be stale/merged — check `git log --oneline -5` on both the worktree's current branch and `master` before assuming they're related, they weren't). Each plan doc lives permanently in `docs/superpowers/plans/` — committed to `master` as its own follow-up commit after the feature merge, not squashed in. Same pattern worked cleanly five times in a row; keep using it.

One recurring hiccup: this session's worktree is at `~/jobwatch/.claude/worktrees/reply-instructions`, a separate checkout from `~/jobwatch` (the main repo root). Local-only state — `.env`, `jobwatch.db`, uncommitted files like `scripts/daily-summary.sh`'s local modification — only exists in the main root, not the worktree. Merges to `master` and any command needing real local data (running a real poll, adding a real secret to `.env`) have to happen `cd`'d into the main root, not the worktree; the harness resets the shell's cwd back to the worktree after each `cd`-out command, so chain everything you need into one Bash call rather than relying on cwd persisting across calls.

## Known gaps / explicitly deferred, not forgotten (carried forward, unchanged this session)

## Verification habits that mattered this session (keep doing these)

- For every new provider/API integration, hit the *real* endpoint with `curl` before writing a line of Go — web3.career's response-shape inconsistency (silently dropping fields under certain query params) would never have been caught by reading their docs page alone, which itself didn't render a sample response (JS-rendered docs site, `WebFetch` couldn't extract it).
- After any deploy, verify byte-identity (`md5sum` local vs `ssh ... md5sum`) and actually run the poll/build/compile on the server, not just check the GitHub Actions run went green.
- After any resume-template change, actually compile with `tectonic` and check `pdfinfo`/`pdftotext` output — a LaTeX source diff alone doesn't tell you if the change pushed the page count over 1.
- When a stray/duplicate untracked file shows up in a fresh worktree branch (this happened three times this session with plan docs), check `diff <file> <(git show origin/master:<file>)` before assuming it's a conflict — it was always an already-committed duplicate, safe to delete.
